## 3. Working rules to carry into implementation

Keep Dastan under its own app/test paths, with Core free of infrastructure dependencies. Reuse current central versions and the repository's English documentation conventions. New UI resources must have real translations required by the repository; do not fill all translation files with English to pass a key-count check.

The no-attribution rule means the execution prompt should remain an external handoff artifact by default. Import the product specifications selectively after checking applicable instructions; do not add tool-specific configuration, attribution or unrelated generated artifacts to tracked files. Commit/push behavior, owner identity and hooks follow the live repository rules and applicable user authorization. These documents do not grant public deployment, paid resources or access to another product's retained environment.

Generated build/review output belongs under the repository's approved `artifacts` area. Preserve pre-existing work, retained evidence and unrelated projects. Never use broad cleanup, change global Git/SDK settings, bypass a hook, or weaken an existing assertion to obtain a passing result. Apply existing native-device instructions to their stated native scope; do not trigger mobile financial workflows merely because Dastan is added to the same solution.

## 4. Bounded technical checks

These are planned exercises, not completed validation. Use the smallest representative case that resolves each decision. Start with the recommended architecture, investigate at most one concrete alternative for a failed requirement, record the outcome and continue implementation. Do not let discovery become a separate indefinite phase.

| Check | M0 exercise | Later extension / exit evidence |
|---|---|---|
| **SPIKE-TIME** | Round-trip an exact calendar date, year-only precision, BCE/CE boundary, uncertain point, actual duration with uncertain endpoints, open end, anchored 50–60 million-year range and fictional sequence. Reject incompatible comparisons. | Choose minimum value types and query/axis rules; narrative values never become calendar years. Full calendar conversions and large historical visualizations can follow concrete content needs. |
| **SPIKE-UI** | Render the small permitted relation graph plus list, vertical story and parallel participant lanes; preserve selection/back state at 360/412px and desktop widths. Use correct association roles, including mentioned rather than present participants. | Record readability, keyboard route, language/direction, rendering conditions and any observed delay. Compare one alternative renderer only if a real criterion fails. |
| **SPIKE-MEDIA** | Use the bundled original still and video after explicit reading boundary 2; verify gallery inclusion, captions, attribution, playback and an unavailable external-image state. Keep sample data outside public static assets. | Public media delivery works without museum downloads. Synthetic private fixtures remain test inputs; real authorization, revocation, private media URLs and private offline behavior must be proven before personal features ship. |
| **SPIKE-INTEGRATION** | Build the minimal Core/Web boundary, isolate two users' language and reading state, test deep links, reconnect behavior, manifest scope and the available browser's install/update behavior. | Record actual SDK/browser/OS and commands. No MAUI workload, separate identity service, production database or cloud account is needed merely for the local read-only slice. |

Time and integration risk checks should immediately inform the first implementation commit; UI and media checks evolve into the running vertical slice. Findings belong in short ADRs linked to [document 20](20-implementation-plan.md), with evidence and a reason to revisit the choice.
