# D-354 complete-history storage regressions and withdrawn row packet

## Outcome

Keep the production complete-history scalar reader unchanged. A bounded complete-row UTF-8 JSON
transport preserves the tested financial data but makes the tenfold Android read slower. It is
withdrawn before any main APK or production commit. This is a rejected direction, not a Home speed
improvement, runtime/GC/ANR fix or completion of QA-06. Do not repeat the unchanged packet or the
previously rejected standalone date decoder without materially new evidence.

## Candidate evaluated, not shipped

The candidate retains all32 original scalar columns, model mapping/transaction/interceptor authority,
null bitmap, original ordering and required-null/coercion fallback. For ordinary storage it additionally
constructs one bounded JSON array and synchronously decodes every field from its borrowed UTF-8 span.
The pre-construction size guard sends large rows to the original provider. Tags and timestamps retain
the original model converters and conversion-error order. Only the precise missing-json_array
capability error retries the original scalar query. No schema, index, native library, KDF, pooling,
key, backup, permission, commercial rule or UI layout is changed.

The [official SQLite JSON documentation](https://www.sqlite.org/json1.html) describes built-in JSON
support, array construction and literal-string handling. Its BLOB limitations motivate original
provider fallback rather than guessing a new GUID/text representation. The proposal is a complete-row
transport experiment, not another standalone ASCII-date decoder or a native fork.
