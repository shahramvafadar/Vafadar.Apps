generation for ordinary non-NativeAOT publishing, so changing Mono AOT mode or
setting PublishAot is not a prerequisite for that proposal. However, the same
documentation explicitly calls query precompilation highly experimental and
unsuitable for production, warns about generated size and provider compatibility,
and excludes some query and captured-converter shapes. A possible mechanism is
not a qualified application speedup.

Current package declarations and the local EF tool are 10.0.12. The original Home
reader and quick-resource reader receive ZananceDbContext as a method parameter.
[Issue38030](https://github.com/dotnet/efcore/issues/38030) reports parameter and
primary-constructor query-discovery failures on EF10.0.5/Npgsql and is closed as
a duplicate of [issue35887](https://github.com/dotnet/efcore/issues/35887), not as
evidence of a fix shipped in this application's SQLite version. This is a
compatibility concern, not a reproduced current failure. No parameter-alias
workaround, provider substitution or unsupported query rewrite is adopted.

Do not introduce this experimental interceptor path into the shipping app on
these facts. No package download, generator invocation, build, benchmark, test,
device, authentication, financial or cleanup action is necessary for this finite
admission. This does not reject all supported EF optimizations or establish that
the original queries are optimal. A subsequent candidate must retain every
field/converter/null/order contract, original EF command interception, captured
file/transaction and all final source/rights checks. It needs a fixed correctness
and performance protocol before a new trial; no old rejected candidate is rescued.
