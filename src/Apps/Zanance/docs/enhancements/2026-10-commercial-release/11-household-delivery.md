## Cryptographic component review (2026-10-16)

Use maintained jose-jwt5.3.0 standard JOSE, not a new cipher, KEM or ad-hoc key-agreement scheme.
Latest stable was checked against the official NuGet index, tagged release (2026-03-27), MIT licence,
published security page and source algorithm registrations. Its net6 target has no dependencies.
No automatic metadata/key discovery, token logging or authentication/provider component is required.

Selected suite: ES256 signed content inside authenticated JWE A256GCM; direct32-byte epoch keys for
records, RSA-OAEP-256 for approved device grants. The library supplies framing, IV generation,
OAEP/MGF1 SHA256 and strict16-byte GCM tags. Disable every unused signing/key-management/encryption
algorithm and all compression. Use dedicated strict VerifyBytes/DecryptBytes, never decode-by-header
selection, unsigned tokens, RSA1_5, SHA1 OAEP, remote key resolvers or a custom crypto provider.
A bounded reflection-free JSON mapper handles headers only, retaining maintained cryptography and
binary payload methods for Release/AOT. Exact purpose/group/epoch/operation/recipient and signer bind
every decrypted message. The invitation/device approval flow must confirm joint public fingerprints.

IdentityModel8.23.0 was initially considered (official current release2026-09-21), but source/strict
compilation established that its supported RSA key-wrap suite lacks RSA-OAEP-256. The failed compile
is retained in household-production-first-build.log; the dependency and unsupported implementation
were replaced before any integration or acceptance claim. No fallback to SHA1 or new custom provider.
Bouncy Castle C#2.7.0 was reviewed but its official C# tree has no HPKE facade; Java API documentation
is not C# support. No private HPKE port. These rejected candidates are not shipped dependencies.
This selection is not external cryptographic audit, forward secrecy, post-quantum security or
acceptance on Android/iOS. Original Release/AOT native use and adversarial interoperability remain
required in this complete batch. Device compromise and retained/exported plaintext cannot be erased.

## Integration design to implement inside this batch

- A household owns a dedicated protected financial profile. Its explicit creation review can copy selected
  source accounts/history into that separate ledger; source personal data remains unchanged. The review must
  state that future personal-source edits are separate, never promise an implicit live link or publish the whole
  private profile. Joining starts with only the household ledger. No portfolio total sums copies per member.
- Project selected rows and only their dependencies. Private-side transfers use a neutral, excluded counterpart
  with no source private id/name/balance/currency; preserve the selected side's actual units/amount/date and
  transfer classification. Unselected plans, holdings, estimates, rules, filters and other-account budgets never
  enter automatically. Explicit optional selections and a complete pre-write review govern extra shared content.
  Preserve financial validation; nullable private references may be detached or independently scoped opaque ids,
  never guessed financial values. Full original graph validation must prove the final projected state.
- Shared cost attribution is separate from cash postings. A linked shared-account expense/refund remains the
  one ledger movement. Private payments create no invented shared-cash entry. All positive explicit allocations
  sum exactly to one cost; cumulative refunds cannot exceed original cost/person shares. Report attributed costs,
  shared-account payments and private advances separately. Do not infer ownership/contributions of opening joint
  cash. Only actual private advances/refunds and explicitly confirmed repayments affect private advance balances.
- Reuse original row merge, graph/ledger validation, occurrence uniqueness, durable outbox/review/apply and blob
  capture, not a new financial algorithm. Abstract the original transport and add a household encrypted adapter.
  Complete graph merge/validation occurs on actual clients; opaque service publication is a serial CAS against
  the observed cursor, membership and epoch. Role checks happen on every resource/request. Invalid encrypted
  finance from a malicious authorized writer is refused by clients without partial financial application.
- A logical operation keeps its id. Distinct staging attempts bind observed predecessor/epoch; only one attempt
  can commit. Lost acknowledgements return the original immutable result. Do not regenerate a successful packet
  or treat a count as an authenticated prefix. Durable client ciphertext plans survive process exits/retries.
- Client-keyed HMAC-SHA256 addresses hide table/key/plain-blob-hash guesses from the service. The independent
  32-byte address key stays client-side and stable across epochs. Record/tombstone/blob pieces are signed then
  encrypted; context binds scope/epoch/operation/recipient, inner payload binds record/version/authority. Upload
  bounded opaque parts, then one signed complete ciphertext digest/previous-head transaction. Retain bounded
  authenticated history/receipts until clients apply or an explicitly expired operation requires fresh review.
- Original readable personal HTTP must never handle a household profile. Persist an explicit connection kind,
  route foreground/UI by scope, and fail closed before construction can send household clear rows. Apply current
  viewer/revoked/grace authorization at actual data write boundaries as well as UI and service. Internal verified
  feed application has its own scoped maintenance authority, not an owner-role bypass available to editors.
- Each room has a separately pinned owner-root signing/recipient identity and per-device signing/recipient keys.
  Device private keys remain inside protected local storage; service stores only public keys and encrypted grants.
  Owner root signs complete membership versions linked to the exact prior hash. Clients verify the whole chain
  from local creation or the independently received invitation checkpoint; server key-directory substitution is
  insufficient. Active members get epoch grants only to their exact approved keys; older epochs remain available
  through separately wrapped grants when shared history access is intended.
- Invitations reserve a seat for at most48 hours, are single-use and contain an independent256-bit capability
  unrelated to encryption keys. The recipient explicitly accepts and signs its identity/key claim. Owner then
  independently verifies its public fingerprint before signing acceptance and distributing keys. A pending seat
  or new login never receives finance. There are six accepted/reserved identities and eight devices per identity;
  historical contacts do not grant access or consume active membership seats.
- Every effective membership/device/role change advances membership and encryption epoch. Revoke/leave immediately
  stops server access and freezes writes until fresh grants exclude removed devices. Already downloaded/exported
  content cannot be recalled. Owner transfer requires old-root consent and new-root acceptance; the target generates
  its own root/new epoch so a departing old owner does not learn the future key. A retained old owner receives
  only its explicitly chosen remaining role, never the new owner's private root.
- A lost-session rebind requires the existing approved device private key plus actual new authenticated session.
  New device approval is separate. Optional owner recovery uses a separately held encrypted recovery kit/private
  recipient and user-held random protection code, neither remembered in the app. Store only its public recipient
  for automatic encrypted epoch/root updates. Recovery requires real owner login, kit proof, root continuity and
  rotation away from lost devices/root. A password reset alone never decrypts household content.
- Portable exports scrub device keys, role/grant/session authority and outboxes; financial costs/contact labels
  remain owned data. Restore stays detached until explicit current-state review/approval, never replaying old deletes.
  Device-only automatic copies are not a substitute for a portable export or a separately held recovery kit.
- Apply approved expiry on authoritative server time: active until actual verified expiry, then30 days read/export,
  then90 days server retention, deletion due at120 days. Revocation always wins. Local cached/exported-copy limits
  are explained. No verified paid grant is manufactured; unverified local test allowance must not enable public
  household hosting or commercial enforcement. Operational backup/deletion replay remains a live-hosting gate.

These choices remain the complete-batch target. The concrete service/client work below does not constitute
finished app integration, a privacy/release acceptance claim or independent cryptographic audit.
